# v0.2 repository audit

Audit date: 2026-08-25. Baseline reviewed: v0.1.0 at commit `cb44017`.

## Existing architecture

The project is a small, layered Python package. `loader` accepts bounded local JSON in four common MCP catalog shapes. `normalizer` converts aliases into strict `ToolDefinition` models, NFC-normalizes strings, rejects oversized individual text values, preserves unknown fields, rejects conflicting aliases, and rejects duplicate tool names. `canonicalizer` and `fingerprint` produce deterministic SHA-256 identities. Independent detector classes consume normalized tools and emit typed `Finding` values. The risk engine confidence-adjusts findings, caps categories, applies two documented synergies, and assigns a severity band. The CLI coordinates scanning, baselines, comparisons, fingerprints, rule validation, explanations, and inert terminal/JSON/CSV/SARIF reporters.

Baselines store full/component hashes and structural summaries rather than raw descriptions or schema values. Drift comparison covers additions, removals, conservative renames, descriptions, input/output schemas, annotations, execution metadata, and general metadata. Custom YAML rules are data-only, safe-loaded, bounded, and use literal matching.

The normal scan data flow is:

`bounded JSON -> normalization -> detectors/rules -> risk score -> report`

The fingerprint path branches after normalization, while baseline comparison consumes fingerprints and privacy-conscious summaries.

## Existing strengths

- Clear separation between hostile input handling, normalization, detection, scoring, and presentation.
- Deterministic behavior with strong Unicode and canonicalization tests.
- Stable, explainable built-in IDs (`PI-001` through `CAP-001`).
- No tool invocation, URL following, icon download, telemetry, template evaluation, or executable rule configuration.
- Good failure semantics and CLI exit-code documentation.
- Baseline privacy is better than storing complete catalog snapshots.
- Machine-readable reporters account for ANSI/terminal content and CSV formula injection.
- The baseline suite passes 168 tests with 97.29% branch-aware coverage.

## Problems discovered

- There is no labeled corpus or empirical detector-quality measurement, so detector behavior is tested rule-by-rule but not as an end-to-end classification system.
- The CLI owns the reusable `analyze` pipeline. Evaluation or future retrieval would otherwise need to import presentation code or duplicate scan logic.
- Exact duplicate findings can increase a category score until its cap. This is deterministic but lets duplicate detector/rule output inflate risk without adding evidence.
- Custom rule files have no pack identity/version, so experiment results cannot fully identify the evaluated rules.
- There is no acknowledged-finding suppression format. Users must disable or edit rules, losing the reason and scope of an exception.
- Reproducibility metadata (application, rule pack, corpus, Python, UTC timestamp) is absent because no experiment report exists.
- The local virtual environment in this checkout references a removed Python installation. This is a workstation issue, not a repository defect; CI and the source baseline are healthy.

## Technical debt

- Detector descriptions, registry explanations, and default rule-pack metadata are maintained in separate forms and can drift.
- Categories are free-form strings. Existing public finding serialization makes a breaking enum conversion undesirable in v0.2, so evaluation must validate its known taxonomy explicitly.
- Several detectors intentionally use broad vocabulary. Unit tests cover immediate examples, but systematic borderline/false-positive analysis is missing.
- `DEFAULT_RULES_PATH` assumes a source checkout; it is not a packaged resource. v0.2 evaluation should not silently depend on this path.
- CLI error handling collapses unexpected exceptions into a generic message, which is safe but can make local diagnosis harder. Debug tracing remains intentionally out of scope for this release.

## Security observations

- Regular expressions are fixed in code, short, and avoid user-controlled regex evaluation. Custom patterns are bounded literal strings.
- YAML uses `safe_load`, Pydantic rejects extra rule keys, and input/rule counts and sizes are bounded.
- Evidence is length-bounded and ESC-neutralized; redaction works before reporting.
- Recursive traversal was initially bounded only indirectly by the 10 MiB file limit. The hardened implementation rejects metadata deeper than 64 levels, oversized strings/keys, and duplicate keys produced by Unicode normalization; it never truncates accepted security-significant content.
- A local MCP catalog feature must be opt-in, localhost-only in this release, timeout/size/count bounded, and limited to `tools/list`. It must never execute a command from metadata or invoke a discovered tool.

Detector review found no user-controlled regular expressions, catastrophic nested quantifiers, unbounded content decoding, or cross-tool mutable state. `PI-001` and `HID-001` now inspect separate field-addressable text values across descriptions, schemas, annotations, execution data, metadata, and unknown fields, with negation and bounded educational-reference handling. Legitimate privacy wording remains a documented false-positive source. `SEC-001` scans all text fields and lowers (rather than removes) legitimate authentication context. `SCH-001` uses offline dialect validation; `SCH-002` reports one bounded aggregate. `MIS-001` uses conservative high-impact category vocabulary and can overread generic words such as “record.” Obfuscation decodes nothing and reports at most one invisible-control finding plus bounded structural indicators. `CAP-001` is deliberately informational because declared high-impact functionality is not inherently malicious.

## Changes proposed for v0.2

1. Extract scanning into a presentation-independent engine used by both `scan` and evaluation.
2. Add validated, versioned corpus models and a deterministic evaluator with binary/category metrics, confusion matrix, timing, and FP/FN records.
3. Add a balanced synthetic corpus with realistic borderline examples and documented ground truth.
4. Deduplicate equivalent rule/category contributions in risk scoring while preserving category caps and synergies.
5. Add lightweight rule-pack metadata and data-only, justified suppressions.
6. Add opt-in, localhost-only SDK `tools/list` retrieval after the offline evaluation path is complete.
7. Extend documentation, CI, tests, changelog, and version metadata without changing established rule IDs.

## Things intentionally NOT being changed

- Existing rule IDs, finding schema, fingerprint algorithm, baseline privacy model, severity bands, category caps, or synergy values.
- The default offline scan workflow and existing output formats.
- MCP tool execution: the inspector will never call a discovered tool.
- Remote crawling, arbitrary command spawning, icon/URL fetching, credentials, telemetry, LLMs, ML classifiers, databases, accounts, dashboards, SaaS, or deployment infrastructure.
- Signed baselines. The current model can be enveloped later; a PKI design would distract from the evaluation objective.
